Agent Passport

Identity is not authority. An AI agent can be correctly identified and still act beyond what its principal allowed. Agent Passport lets an agent prove, before the money moves, exactly what it is allowed to do, who assured it, and whether that authority is still current. Delegation can only narrow authority, never expand it.

What it is

Two components, one engine. The Standards Review Assistant (the brief's KYA standards evaluation tool) sits with the authority before issuance: it reads the evidence, maps it to a versioned rule pack, generates adversarial tests, runs them through the bank's own engine, and recommends. A named officer decides and signs. The Cryptographic Delegation Verifier (the brief's cryptographic authorization validator) sits with the relying party at action time: nine ordered checks, deny by default, over a three-signature envelope, answering ALLOW, ESCALATE or DENY with a rule, a reason code and a signed receipt. Both are needed: a credential nobody verified at issuance is a rubber stamp, and a verifier with no assured issuer has nothing to trust.

The passport is an envelope of three independently signed claims: the authority's assurance of the provider, the provider's identity claim for its agent and key, and the customer's payment mandate naming payees, limits and expiry. Each party signs only what it is entitled to say. The bank checks all three, then its own ledger for the cumulative limit, then the supervisor's condition. Refusals are logged as violations; a repeated pattern raises a supervisor alert; the authority can suspend, investigate, revoke or reinstate, and the mirrored mandate on the vouch rail follows.

What it is not

  • Not a replacement for the provider's licence, the customer's contract or the bank's own account mandate. It references them and adds a fourth, machine-verifiable layer.
  • Not a scoring or reputation system. Every outcome is a rule with a source; no black-box score.
  • Not an autonomous regulator. The model reads and drafts; rules decide; a human signs; nothing auto-approves.
  • Not a current legal requirement. This demonstrates a proposed assurance framework on synthetic data. No supervisor issues agent passports today.
  • Not a blockchain. Signatures, a registry and a hash-chained, replayable log.

Why it matters now

Agents already read invoices and initiate payments. The invoice is the attack surface: change one account number on a genuine-looking document and a capable agent will pay the wrong account. Named-beneficiary mandates, checked cryptographically at the moment of payment, stop that regardless of how convincing the document was. Agent Passport addresses the same delegation-gap problem as Visa TAP and ERC-8004, within the FCA-regulated payment institution framework.

Technical standards

  • JWT (RFC 7519), OIDC-compatible, as the container for all three claims; W3C Verifiable Credentials pattern, JWT profile, no JSON-LD wrapper.
  • Ed25519 signatures, EdDSA (RFC 8037); keys generated on this server.
  • Scope as OAuth 2.0 Rich Authorization Requests (RFC 9396) authorization_details inside the customer-signed mandate.
  • Agent key binding by cnf (RFC 7800), proven at application by a signed challenge and on every instruction by a signature; workload-identity guarantees equivalent to SPIFFE SVID.
  • Registry status read at action time; status-list-style revocation by registry flag; a bank-held ledger for cumulative limits; sha256 hash chain with exact replay.
  • Agent and authority keys are compatible with W3C did:key resolution. Full DID document support is a production extension.

Regulatory context

Framed as a proposed FCA Agent Assurance addendum extending the Payment Services Regulations 2017 for authorised payment institutions that deploy autonomous agents. The named-beneficiary mandate check aligns with FATF 2025 AML/CFT guidance on payee verification. The authority in this demo is jurisdiction-neutral, "the national payments supervisor (demo)"; nothing here is an FCA process or product. Every rule carries a CURRENT or PROTOTYPE label and a source, listed below.

Where the model sits, and where it does not

Gemini is used at the edges only: reading the evidence pack and invoices into fixed schemas with a verbatim quote per fact, and phrasing a draft file note. It never checks, scores, approves or verifies. If the API is unavailable the system falls back to a deterministic fixture and says so. The consequential middle is the rule pack {{ pack.id }}, so the same inputs always give the same decision.

What is simulated

  • The registers, the firms, the bank, the accounts, the invoices: all synthetic.
  • The agent and the customer's signing ceremony run inside this server so the demo can show a copied passport, an unsigned mandate and a manipulated invoice failing.
  • Sub-agent delegation, multi-bank totals, an incident workflow beyond the exception panel, and attestation of the running software are roadmap.

What we do not claim

That any supervisor issues agent passports today; that the passport replaces the provider's licence, the customer's contract or the bank's own mandate; that a signature proves an agent is safe or correct; that a valid passport compels a bank to execute; that this is production cryptographic infrastructure.
